# 01 · 项目需求与技术方案

> 真源 ProofMate · 文档证据审查台
> 赛道：TextIn xParse 实用价值
> 本文档说明产品目标、用户流程、技术架构、xParse 的职责边界、OpenVINO 与 Qwen 的协同方式，以及凭证管理与错误处理策略。

## 一、产品目标

ProofMate 要解决的问题是：**用户手里有一堆材料，却说不清哪些结论真的被原文支持。**

产品把上传的 PDF、图片、扫描件和项目文档整理成一份可回查的**主张—证据档案**，明确回答五个问题：

1. 哪些结论已经有原文证据支持；
2. 哪些结论与材料存在冲突；
3. 哪些结论仍然缺少证据；
4. 每条判断引用了哪份材料、哪段原文；
5. 用户下一步需要补充什么材料。

产品的硬约束是：**模型生成的内容不直接等于事实。** 每条证据必须同时保留来源文件、原文摘录、提取方式和人工确认状态；没有原文可回查的结论只能停留在"待核对线索"，不进入已确认事实。

档案顶部展示的分数是**材料审查进度**，不是事实真伪的概率。总分按覆盖度 35%、一致性 25%、时间信息 15%、复核完成度 25% 加权，每条主张再按核心 2、高 1.5、普通 1 加权（`src/domain/audit.ts`）。

## 二、用户流程

```
① 投递材料            ② 清点与抽取              ③ 端侧初审
   首页 / 案例库   →   ScanSequence 三仪表   →   OpenVINO Qwen3-4B INT4
   拖入或选择文件      文字提取仪 → OCR 仪        生成候选主张（带依据/风险/补证建议）
                                                          ↓
⑥ 导出与补证  ←  ⑤ 云端复核未解决项  ←  ④ 人工确认入档
   答辩摘要导出     百炼 Qwen 只复核未解决主张      审阅者对照原文件确认关系
```

关键节点说明：

| 阶段 | 界面位置 | 行为 |
|---|---|---|
| ① 投递 | `src/features/onboarding/FileDropzone.tsx` | 校验格式与 10MB 上限，支持 PDF / MD / TXT / CSV / JSON / 图片 |
| ② 抽取 | `src/features/onboarding/ScanSequence.tsx` → `buildImportedAudit.ts` | 按扩展名分流：文本直读、PDF 走 PDF.js、图片与扫描 PDF 走 xParse OCR |
| ③ 端侧初审 | `src/features/settings/RuntimePanel.tsx` | 调用 `local-ai/` 的 OpenVINO 服务，结果需人工点"确认并加入档案" |
| ④ 人工确认 | `src/features/audit/RiskInspector.tsx` + `AuditDashboard.tsx` | 人工确认关系后 `reviewedByHuman = true`，才计入评分 |
| ⑤ 云端复核 | `server/qwenClient.ts` | 只发送未解决主张与上传原文片段，返回摘录仍须与原文件逐字核对 |
| ⑥ 导出 | `src/features/export/buildReport.ts` | 导出答辩摘要 Markdown |

```
│  /api/local/evidence→ local-ai 证据关系判定                                                    │
└───────────────────────────────────────┬─────────────────────────────────────────────────────┘
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        ▼                               ▼                               ▼
  TextIn xParse                 百炼 Qwen（云端）              OpenVINO Qwen3-4B INT4（端侧）
  图片 / 扫描件 / 扫描 PDF        按需复核未解决主张              隐私优先的第一遍初审
```

### 各层职责

- **`server/xparseClient.ts`**：把图片/扫描件交给本机 `xparse-cli`，取回 Markdown 正文。负责格式白名单、进程调用、超时控制、错误归一化。
- **`server/providerSettings.ts`**：本机凭证读写，落盘 `.proofmate.local.json`（`mode: 0o600`），对外只提供 `providerStatus()` 掩码（例如 `…abcd`），不返回完整密钥。
- **`server/qwenClient.ts`**：百炼调用与返回结构校验，含 `provider_not_configured` / `provider_timeout` / `provider_error` / `provider_ready` 四态。
- **`src/features/onboarding/extractFileText.ts`**：客户端抽取分流与 `ExtractionMethod` 标注（`browser-text` / `pdfjs` / `xparse-ocr` / `none`）。
- **`src/features/onboarding/buildImportedAudit.ts`**：把抽取结果转成 `EvidenceItem`，生成片段、指纹与处理轨迹。
- **`src/features/audit/SourceMaterialPanel.tsx`**：把"提取到什么"和"原文件长什么样"并排展示给用户。

## 四、TextIn xParse 的职责边界

### xParse 负责什么

- 把**图片**（PNG / JPG / JPEG / WEBP / BMP / TIF / TIFF）和**扫描 PDF** 中的文字转成可搜索、可引用的 Markdown / JSON；
- 提供结构化结果：`markdown`、`elements`（含 `Title` / `NarrativeText` / `Table` 类型）、`title_tree`、`pages` 与 `file_id` / `job_id` / `x_request_id` 等可追溯标识。

### xParse 不负责什么

| 不属于 xParse 的工作 | 实际承担者 |
|---|---|
| 判断这段话是"支持"还是"冲突" | 端侧 OpenVINO / 云端 Qwen 给出候选，人工确认 |
| 决定某个结论是否成立 | 审阅者本人 |
| 生成主张、风险边界、补证建议 | 端侧初审与云端复核 |
| 判断材料真伪 | 不做此判断，只做证据关系整理 |
| 文本型 PDF 的正文读取 | 浏览器 PDF.js（避免无意义 OCR） |

**一句话边界：xParse 只负责"把字读出来"，不负责"这些字说明什么"。**

这条边界在界面上被显式写出（`SourceMaterialPanel.tsx` 的 "OCR 的作用" 说明块），并且在数据结构上被强制：OCR 正文只写入 `EvidenceItem.content` 与 `fragments`，初始 `relation` 为 `unreviewed`，`reviewedByHuman` 为 `false`，不会自动变成"已证实"。

### 抽取分流规则（`extractFileText.ts`）

```
.md / .txt / .csv / .json          → browser-text（浏览器直读）
.pdf 且去空白后 ≥ 8 个字符          → pdfjs（浏览器内 PDF.js，不上传）
.pdf 且去空白后 < 8 个字符          → xparse-ocr（判定为扫描件）
.png/.jpg/.jpeg/.webp/.bmp/.tif/.tiff → xparse-ocr
其他                                → none
```

"8 个字符"这个阈值同时覆盖了"纯图片型 PDF"和"只有页码的 PDF"两种情况——只有页码的 PDF 依然会被送去 OCR，不会被误判为可读正文。

## 五、OpenVINO 与 Qwen 的协同方式

两者不是并联的"两个模型都跑一遍"，而是**串联的两道闸门**，且分工由隐私边界决定。

| | OpenVINO Qwen3-4B INT4（端侧） | 百炼 Qwen（云端） |
|---|---|---|
| 位置 | `local-ai/`，`127.0.0.1:8787` | `https://dashscope.aliyuncs.com` |
| 触发 | 用户点击"使用端侧模型分析" | 用户点击"复核 N 条未解决主张" |
| 输入 | 全部材料正文（`localText`，最多 12000 字符） | 未解决主张 + 对应证据摘要 + 上传原文片段（`cloudText`） |
| 输出 | 带依据、风险边界、补证建议的候选主张 | 对未解决项的复核建议 |
| 隐私 | 材料不出本机 | 明确提示"会把未解决主张及上传原文片段发给百炼" |
| 结果去向 | 人工点"确认并加入档案"后才写入 | 人工点"确认 N 条云端发现并加入档案"后才写入 |

协同要点：

1. **先端后云。** 端侧初审覆盖全部材料；只有当主张仍未被解决（`status !== 'verified'`）时，云端复核按钮才可用（`scopeCount` 为未解决数量，为 0 时按钮禁用）。
2. **云端只做复核，不做新增。** `qwenClient.ts` 的 system prompt 明确"只复核输入中编号 1 至 N 的【待复核主张】，不得新增主张"，并用 `claim_index` 把返回结果绑定回原主张；`containsUnsupportedIdentifier()` 会拦截模型编造的、输入材料中不存在的标识符。
3. **两者产物都必须过人工闸门。** `reviewMerge.ts` 负责新增/更新/合并/解决四类变化的计算，并按轮次汇报"剩余 N 条待复核"，没有变化时标记为已收敛。
4. **评分只认人工确认过的原文关系。** `domain/audit.ts` 中，导入档案（`id` 以 `import-` 开头）的支持证据必须满足 `reviewedByHuman === true` 且 `findGroundedSource()` 能在原文件正文里按指纹找到摘录，才计入覆盖度。

## 六、凭证管理

### 读取来源

凭证只从**环境变量**或**本机设置文件**读取，从不出现在对话、日志或前端产物中：

| 变量 | 用途 | 读取位置 |
|---|---|---|
| `XPARSE_APP_ID` | TextIn xParse App ID | 环境变量 / `.proofmate.local.json` / 设置页 |
| `XPARSE_SECRET_CODE` | TextIn xParse Secret Code | 同上 |
| `DASHSCOPE_API_KEY` | 百炼 Qwen | 环境变量 / `.proofmate.local.json` / 设置页 |
| `QWEN_MODEL` | 百炼模型名（默认 `qwen-plus`） | 环境变量 |

### 安全设计

- `.proofmate.local.json` 写入时使用 `mode: 0o600`（`providerSettings.ts`），并已被 `.gitignore` 忽略；
- `/api/settings` 的 `GET` 只返回 `providerStatus()`，即 `{ configured: boolean, hint: '…最后4位' }`，**前端拿不到完整密钥**；
- 所有外部调用都在 Node 侧（Vite 中间件）完成，密钥不进浏览器 bundle；
- 设置页三个输入框均为 `type="password"` + `autoComplete="off"`，提交后立即 `form.reset()`；
- xParse 调用时密钥通过子进程 `env` 传入 `xparse-cli`，不写入命令行参数，避免出现在进程列表里。

### 本机实际配置状态（不含密钥内容）

- `.proofmate.local.json`：`textinAppId` 已配置（32 字符）、`textinSecretCode` 已配置（32 字符）；`dashscopeApiKey` 未配置。
- `.env.local`：`DASHSCOPE_API_KEY`、`QWEN_MODEL` 已设置。
- 本次 xParse 调用使用 `--profile workbuddy` 走 CLI 已登录的凭据档案，未在命令中传递任何密钥。

## 七、错误处理

### 三层错误状态

| 层 | 机制 | 用户看到什么 |
|---|---|---|
| 抽取层 | `ExtractionFailure(method, message)` | 材料卡片上的失败说明 + 处理轨迹条目 |
| xParse 层 | `XParseFailure(code, message)`，5 个状态码 | 区分"超时 / 未安装 CLI / 格式不支持 / 无结果 / 服务报错"的中文提示 |
| 模型层 | `QwenResult` 四态 | `provider_not_configured` / `provider_timeout` / `provider_error` / `provider_ready` |

### xParse 失败状态归一化（`server/xparseClient.ts`）

```ts
type XParseFailureCode =
  | 'unsupported_document'  // 格式不在 xParse 支持范围
  | 'cli_unavailable'       // 本机未安装 xparse-cli
  | 'parse_timeout'         // 超过 120 秒未返回
  | 'missing_result'        // 调用完成但没有 Markdown 产物
  | 'parse_failed';         // 其他失败（优先透传 xparse_error.v1 的服务端 message）
```

`toXParseFailure()` 会把 Node 的原始进程错误（形如 `Command failed: xparse-cli.cmd parse C:\Temp\...`）翻译成上述状态，**不再把本机临时路径和 CLI 原始报错直接暴露到页面**；同时它会解析 `xparse-cli` 在 stderr 输出的 `xparse_error.v1` JSON 对象，把服务端自己的 message 原样带出。

### 空结果与失败必须可区分

`buildImportedAudit.ts` 的 `unresolvedExcerpt()` 把"没有文字"拆成三种互不相同的提示：

1. **调用失败**：`xParse OCR 解析失败：<具体原因>`
2. **OCR 成功但没识别到字**：`TextIn xParse 已返回结果，但这份图片或扫描件没有识别到可核对文字；请确认扫描清晰度或改用更清晰的图片后重试。`
3. **浏览器读取为空**：`浏览器已完成文件清点；材料未提取到可核对文字。`

失败材料不会从档案里消失，而是以"未确认关系"保留，并在处理轨迹中列出具体文件名与原因。

## 八、已知限制

- 云端复核会把未解决主张与上传原文片段发送给百炼，界面上已明确告知；
- OpenVINO 端侧服务需要用户自行按 `local-ai/README.md` 启动，未启动时界面显示"服务未启动"；
- 扫描件的识别质量取决于原图清晰度，OCR 误识别字符会一并保留在原始提取内容中供人工核对；
- 评分是审查进度，不是事实真伪概率；
- 本机档案自动保存只保留提取正文与分析结果，不保存原文件；刷新后需重新关联原文件才能预览。
