## 二、发现的问题汇总

| # | 问题 | 严重度 | 是否修复 |
|---|---|---|---|
| 1 | xParse 失败时把 Node 原始进程错误（含本机临时路径、`Command failed` 字样）直接显示给用户，且无法区分超时 / 未安装 CLI / 服务报错 | 中（影响第 8 项检查） | ✅ 已修复 |
| 2 | 客户端图片白名单（`png/jpg/jpeg/webp`）窄于服务端白名单（`+bmp/tif/tiff`），BMP/TIFF 扫描件在上传阶段就被静默丢弃，永远到不了 xParse | 中（影响第 1 项检查，"扫描材料"主场景） | ✅ 已修复 |
| 3 | "OCR 成功但返回空文本"与"浏览器读取为空"共用同一条提示，用户无法判断该不该重扫 | 低（影响第 8 项检查） | ✅ 已修复 |
| 4 | 没有直接编辑 OCR 文本的输入框 | 低（第 5 项检查） | ❌ 未修复，见"剩余限制" |

**问题 2 的依据**：真实调用 `xparse-cli quota --output json --profile workbuddy` 返回服务端支持的 `content_types`：

```json
"supported_content_types": [
  "application/pdf", "image/jpeg", "image/png",
  "image/bmp", "image/tiff", "image/webp"
]
```

服务端明确支持 `bmp` 与 `tiff`，而客户端 `imageExtensions`、`importFiles.supportedExtensions` 与两处 `accept` 属性都不含这两种格式——服务端能力被前端挡住了。TIFF 恰恰是扫描仪最常见的输出格式，因此这是一个真实的场景缺口。

### 修改 1 · `server/xparseClient.ts` — xParse 失败状态归一化

**原因：** 第 8 项检查要求失败与超时状态有清晰提示。修复前 `execFile` 的原始错误被逐层透传到页面，既不可读又泄露本机路径。

**做法：** 引入 `XParseFailure` 与 5 个状态码，新增 `toXParseFailure()` 与 `readXParseServiceMessage()`。

```ts
export type XParseFailureCode =
  | 'unsupported_document' | 'cli_unavailable' | 'parse_timeout'
  | 'missing_result' | 'parse_failed';
```

- `ENOENT` → `cli_unavailable` → "本机没有检测到官方 xparse-cli，请先执行 npm i -g xparse-cli 后重试。"
- `killed` / `SIGTERM` / `ETIMEDOUT` → `parse_timeout` → "TextIn xParse 超过 120 秒仍未返回结果，本次没有生成任何文字；请稍后重试或改用更小的文件。"
- 其余失败 → 解析 `stderr` 上的 `xparse_error.v1` JSON 对象，透传服务端自己的 message；解析不到则回退到固定文案
- 结果目录里找不到 `.md` → `missing_result`（原来会抛出裸的 `ENOENT`）

**顺带修复：** 原来若输出目录不存在，`readdir` 会抛裸错误；现在 `readdir(output).catch(() => [])` 后统一归到 `missing_result`。

**未改变：** 中间件契约（仍是 `{ state: 'parse_failed', message }`）、超时时长（120 秒）、`--api auto` 路由、密钥通过 `env` 传递的方式。

### 修改 2 · 对齐图片格式白名单

**原因：** 问题 2。

**做法：** 在 `extractFileText.ts` 中新增 `bmp`/`tif`/`tiff`，并把图片判定收敛为唯一的导出函数 `isImageFile(name)`，避免各处正则各写一份：

```ts
const imageExtensions = new Set(['png', 'jpg', 'jpeg', 'webp', 'bmp', 'tif', 'tiff']);

/** 与 server/xparseClient.ts 的 supportedExtensions 保持一致，避免扫描件在进入 xParse 之前被丢掉。 */
export function isImageFile(name: string) { ... }
```

同步更新：`importFiles.supportedExtensions`、`FileDropzone` 的 `accept`、`SourceMaterialPanel` 的重新关联 `accept`、`buildImportedAudit` 的 `kind` 判定与 `isImage` 判定（原来是 `/\.(png|jpe?g|webp)$/i` 正则，会漏掉新增格式）。

**未改变：** 10MB 上限、PDF 分流阈值、`ExtractionMethod` 取值集合。

### 修改 3 · `buildImportedAudit.ts` + `SourceMaterialPanel.tsx` — 空结果与人工核对提示

**原因：** 问题 3，以及第 5 项检查中"人工校正入口"的提醒缺位。

**做法：**

`buildImportedAudit.ts` 抽出 `unresolvedExcerpt()`，把"没有文字"拆成三种互不相同的状态：

```ts
function unresolvedExcerpt(file, result) {
  if (result?.error) return `${isImageFile(file.name) ? 'xParse OCR' : 'PDF'} 解析失败：${result.error}`;
  if (result?.method === 'xparse-ocr') return 'TextIn xParse 已返回结果，但这份图片或扫描件没有识别到可核对文字；请确认扫描清晰度或改用更清晰的图片后重试。';
  return '浏览器已完成文件清点；材料未提取到可核对文字。';
}
```

`SourceMaterialPanel.tsx` 的说明块补充："识别结果可能保留误识别字符……请对照右侧原文件逐字核对后再确认关系。"

**未改变：** 失败材料仍保留在档案中且标为未确认关系；处理轨迹的字段结构不变。

## 六、剩余限制

1. **没有 OCR 文本编辑入口。** 用户只能对照原文件确认关系，不能直接修改识别错的字符。若要做，需要改动 `EvidenceItem` 数据模型、`auditDraft` 持久化与 `reviewMerge` 合并逻辑，不属于低风险修复，本次未做。
2. **浏览器不渲染 TIFF 预览。** 新增 TIFF 支持后，右栏 `<img>` 对 `.tif/.tiff` 通常无法显示（浏览器原生限制）。提取正文不受影响，但预览体验有损。
3. **端到端测试未运行。** 见第四节。
4. **BMP/TIFF 受 10MB 上限约束。** 多页扫描 TIFF 常超过 10MB，会被 `validateFiles` 拦下并提示"请压缩后重试"。
5. **xParse 超时阈值为固定 120 秒。** 不可配置；超时后本次不会产生任何文字，需要用户重试。
6. **`--api auto` 不会自动升级到付费模式。** 免费额度用尽时会失败并给出提示，不会静默产生费用——这是设计选择，不是缺陷，但用户需要知道。
7. **本次验证使用免费（未认证）额度。** `xparse-cli auth status --profile workbuddy` 返回 `{"logged_in":false}`，两次解析走的是每日免费额度（`daily_pages_used` 0 → 2）。AppKey 免费包路径本次未被验证。
